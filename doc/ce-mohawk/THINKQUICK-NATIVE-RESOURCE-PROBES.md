# Native resident cache, deleting destructors and cross-resource linked code

November 26, 2026. Step 3 original-runtime research; no CE engine implementation.
Seven new original-only probes execute original cache, memory, item destruction
and linked fetch routines. These extend the prior five unload-order fixtures;
they do not relabel those older callback substitutes as real destructors/cache.
See THINKQUICK-NATIVE-RESOURCE-OBSERVATIONS.json for exact executable, source,
generated bytecode and receipt identities, checked observations and limits.

## Resident cache retain/release

Original memory initializer 0x456fe5 creates the real memory-handle table. Original
allocator 0x456b06 allocates the map, descriptor and data buffers; original lock/
unlock routines populate and access them. The fixture seeds one already-resident
RMAP descriptor with count 1 and valid resident flags. It does not load an archive.

Original cache lock/retain 0x45a126 returns that data handle and increments its
resource retain count. Original release 0x45a2c3 once leaves the payload alive;
the probe reads the actual `REAL` signature. A second release frees the original
allocation, confirmed by original handle-validity query 0x483e1d returning false.
The final probe does not dereference a freed handle. No cache, release or allocator
function is replaced by a fixture callback.

The metadata and FILE synchronization shell are manually populated, using an
original mutex constructor. Original single-thread synchronization mode is enabled
explicitly at 0x49af5c; concurrent locking/scheduling is outside qualification.
This is a real resident-cache primitive test from a seeded state, not validation
of original disk reads, archive parsing, cold population, eviction or reopen.

## Actual item destruction and resource unload

A real original heap allocation is passed to original item constructor 0x4185d0.
Two separate original value cells hold copied item values, both registered with
the item. Calling original scalar deleting destructor 0x41f3e0 with delete flag 1
executes original destructor 0x4189c5 and the original object free. Both surviving
cells become the actual string **~Victim**; the owner's item list is empty.

A second case gives another live item an incoming ScriptLink to the victim.
After real deletion, both registered values are invalidated, but the surviving
incoming link still contains the deleted object's old address. The probe compares
that stored address without dereferencing it or dispatching through the stale
link. This dynamically confirms the bounded absence of incoming-link repair;
it is not a promise that use after deletion has safe semantics.

A third case calls original resource unload **0x4268d3**, with a real heap item and
real resident-cache key. Its original event-7 path runs the actual destructor/free,
invalidates both value cells, empties the item list, clears the active/handle owner
fields and frees the real cached data handle. Repeating unload on the cleared
owner returns without fault. There are **no replacement item-event or release
callbacks** in this case. The resource descriptor was seeded as resident, so this
still does not qualify disk-backed archive teardown or every callback/media type.

## Cross-resource linked bytecode with no fetch bridge

Two independently allocated original resident cache maps own distinct BCOD buffers
and cache keys. Receiver 901's BCOD assigns 99 at expression offset 8. Donor 902's
BCOD assigns 42 at the same offset, with the same symbol spelling. Original field
parsing installs a named handler on donor 902 and a ScriptLink on receiver 901.

Original linked dispatch executes the donor's entry on receiver 901. Crucially,
**original BCOD fetch helper 0x41d38d is untouched**: it follows the temporary code
owner through its resource/key, invokes original cache lock, gets the original
memory pointer, evaluates and unlocks. The caller then observes result 42 and its
code-owner context restored exactly to receiver 901.

- Positive: distinct donor cache key -> result equals 42: true.
- False control: distinct donor key, deliberately expects 43: false.
- Routing control: deliberately gives donor the receiver's cache key -> code at
  the same offset writes 99; result equals 42 is false.

This demonstrates selection between real separately cached code resources, rather
than two logical owners sharing a fixed BCOD bridge. It does not demonstrate two
archives opened by the original file backend or real page/proxy loading. The
minimal page/owner structures, manual CRT/VM setup and application-entry skip
remain explicit. Cache tables are seeded, while dispatch/fetch/evaluation/locks
and the data allocations themselves execute original code.

## Qualification and retained failures

All seven final original cases complete with zero VM errors and pass their
recorded contract checks. They remain **original-only**: no matching CE cache/
destructor observations are claimed, and they are excluded from paired totals.
The existing 60-case paired replay remains separately identified.

Earlier local disk-opening experiments attempted original memory, thread, path,
filesystem and cache initialization against an owned generated MHK. They faulted
in the manually initialized environment (including wrong name-versus-ID lookup
and incomplete synchronization setup) and are retained under native-resources-
01..08; they do not prove the game or its cache fails. Those failed attempts are
not promoted into semantic outcomes. Early resident-state and freed-handle-read
attempts also remain retained; final cases use a valid open-state FILE shell and
query handle validity after release. Disk archive open/read/reopen qualification
remains an explicit step-3 gap.

Reproduce with `probe_mohawk_v5_native_resources.py --original <pinned CarmenTQ.exe>
--root <new disposable directory>`. The tool rejects a different executable hash,
records raw values/strings and fails when native completion or contract checks do
not qualify. Each case gets a fresh debug process; all are terminated afterward.
No original EXE bytes on disk, game assets, accepted executables, profiles or saves
are changed. Implementation remains on hold. Next boundaries include cold disk
cache population, eviction/reopen, matched CE teardown/resource observations,
mutation during active callbacks, and persistence/OS-error UI comparisons.

Fresh paired regression replay: **60 cases, 23 matches, 10 mismatches, 27
unqualified, zero incomparable; overall fail**. The seven new original-only
cases do not change those paired totals. Eleven comparator guards and eight
inventory tests pass. All 21 recorded engine files, 346 CE Test files and the
baseline executable match preservation identities.
