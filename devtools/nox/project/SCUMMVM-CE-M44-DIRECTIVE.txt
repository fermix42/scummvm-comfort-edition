# Nox Archaist — M4.4 Functional Equivalence Closure

## Owner directive — November 18, 2026

The Nox Archaist base v119 native-only ScummVM Comfort Edition port has completed M4.3 acceptance. The subsequent `story.08` investigation1135 identified 16 UNKNOWN reconciliation rows but demonstrated no new native implementation defects.

I am authorizing **M4.4: Functional Equivalence Closure**.

This is an implementation-completion assignment, not an unrestricted reverse-engineering research project.

**Execute the entire assignment autonomously. Do not stop after producing an inventory, research plan, partial analysis or another list of proposed investigations.**

## 1. Architectural intent — authoritative

The objective is a **functionally equivalent native PC clone of Nox Archaist**, using the original base v119 HDV image as the authoritative source of game data and resources.

The objective is NOT cycle-accurate emulation, complete Apple II machine-state reproduction, or instruction-by-instruction equivalence.

If machine-perfect duplication were the objective, an emulator would be the appropriate solution.

The native ScummVM CE engine must reproduce the original game's meaningful player-visible behavior:

- Story progression, quests, flags, events and endings.
- Exploration, maps, movement, transportation and environmental interactions.
- NPC identities, dialogue, schedules and behavior.
- Combat, spells, items, equipment, inventory and character progression.
- Economy, services, recruitment and party management.
- Rules governing access, failure, refusal, consequences and recovery.
- Meaningful ordering of state changes and persistent game-state consequences.
- Original presentation, music, sound and game resources as applicable.

The original disk image remains authoritative for its data and resources. Do not silently substitute reauthored game content, hardcoded approximations or invented behavior.

Native code may interpret and transform those resources into appropriate PC representations.

Apple II-specific implementation details are not requirements unless they materially affect legitimate gameplay.

These include CPU registers, stack layout, ROM calls, bank-switch timing, instruction patching, interrupt delivery, physical disk operations and temporary memory aliases.

Such mechanisms should be understood sufficiently to reproduce their **functional effects**, not reimplemented merely because they existed in the original.

The approved native-only architecture remains mandatory. Do not introduce an original instruction executor, CPU emulation fallback, ROM bootstrap dependency or general-purpose compatibility escape.

### Future modernization

This native implementation is also intended to support future PC-oriented enhancements beyond the ScummVM save system.

Therefore:

- Preserve clean subsystem boundaries and canonical state ownership.
- Prefer explicit native game rules over machine-address-dependent behavior.
- Keep original game mechanics distinguishable from modern enhancements.
- Do not hardcode campaign outcomes or test-specific shortcuts.
- Avoid architectural choices that would unnecessarily constrain future enhancements.
- Do not implement new modernization features in this assignment.

**Functional fidelity now; extensibility for later.**

For each of the 16 UNKNOWN rows, determine whether its unresolved behavior has a meaningful relationship to supported gameplay.

Classify it as one of:

**A — FUNCTIONALLY VERIFIED**

The relevant original behavior and native implementation are equivalent for the defined, supported gameplay domain.

**B — ACCEPTED NATIVE DIFFERENCE**

The original implementation differs, but the difference is intentional, documented and functionally justified. Examples include hardware replacement, memory ownership, safer error recovery and ScummVM save handling.

**C — FUNCTIONAL DEFECT**

A demonstrated discrepancy affects legitimate gameplay or required persistent state. Correct it.

**D — FUNCTIONAL RISK**

A plausible player-visible discrepancy remains unresolved. Identify the precise mechanism, circumstances and impact. Investigate further using targeted evidence.

**E — OUTSIDE SUPPORTED FUNCTIONAL DOMAIN**

The behavior cannot be reached through supported legitimate game operation, or is exclusively a machine-specific implementation detail without gameplay consequences.

An E disposition requires affirmative supporting evidence or an explicit scope exclusion. Absence of a discovered caller is not proof of unreachability.

**F — UNRESOLVED**

The available evidence does not justify any stronger conclusion. State the exact uncertainty, likely player impact and bounded next step.

Do not automatically convert UNKNOWN to VERIFIED.

Do not retain UNKNOWN solely because every theoretical machine state has not been exhaustively modeled.

Distinguish technical uncertainty from actual functional risk.

## 4. Prioritized functional investigations

Resolve the following first.

### S10 — Search rewards and full-inventory failure

Investigate the original sequence involving:

- Search reward eligibility.
- Inventory capacity and physical-slot exhaustion.
- Quest-flag updates.
- Object consumption and repeat Search behavior.
- Reward assignment.
- Failure, fatal and recovery paths.
- Save/reload consequences.

The original may update state before encountering a full-inventory failure, while the native implementation uses staged transactions.

Determine whether this difference is reachable through legitimate gameplay.

Compare meaningful resulting behavior, including the possibility of losing a quest reward, repeating an interaction or corrupting progression.

If the native implementation behaves incorrectly under legitimate conditions, correct it.

An original crash or unrecoverable failure need not be reproduced. A safe PC-specific recovery is acceptable if it does not introduce an unjustified gameplay advantage, progression loss or inconsistent persistent state.

Use focused deterministic validation.

### S03 — Derived dialogue lookup aliases

Investigate the authored mutation targeting derived field133 and its relationship to scene lookup state.

Establish:

- Which dialogue packet or actor produces it.
- Its legitimate activation conditions.
- The state observed before response selection.
- The original mutation's meaningful effect.
- The subsequent redraw and consumer behavior.
- Whether it survives or affects persistence.
- The native equivalent.
- Whether prototype/import/debug-only activation is relevant to supported gameplay.

Resolve the actual functional behavior rather than reproducing arbitrary original memory aliasing.

Correct any demonstrated discrepancy.

### U07 — Unparsed dialogue resource tails

Investigate all 19 indexed tails totaling 4,502 bytes.

For each tail, determine whether it is:

- Valid selectable game data.
- Non-dialogue data or padding.
- A malformed or incomplete resource.
- A legitimately reachable original special case.
- Genuinely unresolved.

Follow the original resource selection and termination behavior sufficiently to determine whether any player-visible dialogue, state change or interaction is omitted.

Do not assume that a native parser rejecting a tail establishes original unreachability.

Do not invent additional quests or dialogue based on ambiguous bytes.

### U02 — Indirect copy/fill behavior

The original investigation established:

- Forward sequential copy with an inclusive source endpoint.
- Fill with an exclusive endpoint.
- Potentially meaningful overlapping-buffer behavior.

Inspect actual gameplay-relevant callers and native equivalents.

Prioritize inventory, party records, recruitment, combat consequences, world records and persistence.

For each supported functional operation, determine whether original copy direction, overlap or boundary behavior affects the resulting game state.

Correct genuine functional discrepancies.

Do not introduce a general Apple II memory-copy execution layer merely to reproduce internal memory mechanics.

## 6. Implementation corrections

For every demonstrated functional defect:

1. Identify the original behavior and its supported gameplay conditions.
2. Identify the native divergence and player-visible consequence.
3. Implement a minimal, coherent correction in the appropriate native subsystem.
4. Preserve canonical ownership and the native-only architecture.
5. Add a focused deterministic regression test.
6. Verify the corrected behavior and relevant adjacent invariants.
7. Document any intentionally different failure or recovery policy.

Avoid isolated special-case patches when a shared native rule is the correct solution.

Do not inject quest flags, alter inventory artificially, manufacture battle results or manipulate saves to make a test pass.

Do not change original source resources to conceal native defects.

Do not spend substantial effort reproducing hardware-specific failures whose functional replacement is already justified.
